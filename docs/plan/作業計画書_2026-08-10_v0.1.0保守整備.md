## 目的

- 現行の `0.1.0` の機能範囲を保ちつつ、依存関係、テスト、CI、外部取得のセキュリティ境界を点検し、確認できた保守上の不足を最小限の変更で直す。
- README 冒頭で、英語話者にも用途、セットアップ、保守状況、非公式プロジェクトであることが分かるようにする。
- `package.json` の `0.1.0` と整合する `v0.1.0` Release を、検証済みの `main` から作成できる状態にする。

## 非目的

- MCP tool、resource、prompt、transport の追加・削除・改名
- 対応サイトやデータソースの追加
- 実績、利用規模、安定性、将来の保守を実態以上に表現すること
- `v0.1.0` のタグまたは GitHub Release の作成

## 進め方

- 変更前に依存関係監査と既存検証を実行し、修正対象を観測事実に限定する。
- 挙動を変える修正は、仕様書の更新後に失敗するテストを追加し、Red → Green → Refactor で進める。
- README、CI、リリース準備は、現行実装と実行結果から確認できる内容だけを記載する。

## 作業項目（完了時に `[✓]`）

- [✓] 依存関係の既知脆弱性と更新状況を確認する。
- [✓] 現行の test / lint / format check / build を実行し、基準状態を確認する。
- [✓] 外部取得の許可リスト、リダイレクト、ログ、レート制限の境界を確認する。
- [✓] 監査で確認できた保守上の不足を、仕様・テスト・実装の順に最小修正する。
- [✓] README 冒頭の英語説明、セットアップ例、保守状況を整理する。
- [✓] `0.1.0` と `v0.1.0` の整合性を検証できる仕組みとリリースノートを整える。
- [ ] test / lint / format check / build と GitHub Actions をすべて通す。
- [ ] 変更内容、参照仕様、影響範囲、リスク、検証結果を記載した PR を作成する。

## 影響範囲とリスク

- 外部取得境界を修正する場合、SCP Data API の通常の JSON 取得は維持し、不正または想定外の遷移だけを拒否する。
- 依存関係更新は既知脆弱性または保守互換性に必要な範囲に限定し、メジャー更新や機能追加を混在させない。
- CI とリリース検証は、ローカルと公開リポジトリで同じ npm コマンドを使える状態を維持する。

## 検証コマンド

- `npm audit --omit=dev`
- `npm audit`
- `npm run format:check`
- `npm run lint`
- `npm test`
- `npm run build`
- `npm pack --dry-run`
