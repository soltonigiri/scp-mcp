# 作業計画書（2026-08-11）: SCP-MCP 改善

## 基本方針

SCP Wiki 由来の知識を、AI が「検索・取得・引用」できる形で、安全かつ出典を失わず CLI 経由で渡すことを維持する。

## 現状

### 維持すべき強み

- Tool は読み取り専用で、SCP Data API を一次データ源としている。
- SCP ページ URL、作者、ライセンスをレスポンスに含め、出典を落とさない設計になっている。
- 外部コンテンツを命令ではなくデータとして扱うための `prompt_injection_detected` を返している。
- 許可ホスト制御、リダイレクト検査、レート制限、監査ログ、ETag キャッシュを備えている。
- stdio と Streamable HTTP の両方を提供し、CLI として利用できる。

### 先に解決すべき問題

1. SCP Data API には同じ `page_id` を持つ別ページがあり、現在の検索索引では一意に扱えない。
2. index / content の配置がコレクションごとに異なり、現在の取得方法では Items、Tales、GOI を一貫して扱えない。
3. 全件インメモリ索引は起動時間とメモリ使用量が大きく、CLI での利用に適さない。
4. ページ作成者と履歴編集者を同じ作者一覧に含めており、正確な帰属情報を返せない場合がある。
5. 長文をページ全体で返すため、必要な節だけを取得し、引用位置を再確認する手段が不足している。
6. npm 実行コマンド、パッケージメタデータ、MCP Registry 登録がなく、導入経路が限られている。

### SCP-173 固有警告の扱い

現行の `media_warnings` は、SCP-173 の本文ではなく、過去に同ページで使用されていた画像に関する特例である。本プロジェクトは個別メディアの利用許諾を判定しないため、この特例を削除する。

次を方針として固定する。

- SCP-173 固有の `media_warnings` フィールド、ハードコード処理、README・要件定義・仕様書・テストの特例記述を削除する。
- 別の警告文への置換は行わない。
- 全ページ共通の `source`、`authors`、`license` と、公式 Licensing Guide への案内は維持する。
- 個別メディアのライセンス判定や利用許諾をサーバーの責務に広げない。

## 目標

1. 主要 Tool が現在の SCP Data API に対して正常に動き、検索から本文取得まで完結する。
2. AI が作者・出典・取得箇所を誤って引用しにくいレスポンス契約にする。
3. 初回検索を CLI として実用的な時間・メモリに収める。
4. 標準 MCP クライアントから能力と読み取り専用性を理解しやすくする。
5. npm と MCP Registry から発見・導入できる状態にする。

## 設計原則

- 一次データ源は SCP Data API のままとし、本文の独自ミラー運営を始めない。
- 検索結果と本文は決定的に返し、サーバー内で LLM に要約・解釈させない。
- 出典・作者・ライセンス・取得位置を本文から分離せず、構造化して返す。
- Tool の乱立を避ける。追加 Tool は必要性を既存 Tool の引数拡張と比較して決める。
- ベクトル DB や GraphRAG は、字句検索の品質評価で不足が確認されるまで導入しない。
- 最新仕様への追従は、互換性と保守性を確認してから行う。
- 各実装項目は独立してテストできる大きさに保ち、不要な変更を混在させない。

## 対象範囲

### 優先度 A: 必須修正

- SCP-173 固有警告の削除
- ライブデータ契約の修正と検索不能の解消
- 作者・帰属情報の正確化
- 検索の起動時間・メモリ使用量の改善

### 優先度 B: 取得機能と配布の改善

- 節単位・範囲指定取得と引用位置情報
- MCP の構造化出力、読み取り専用 annotation、Resource Link
- npm CLI 配布と MCP Registry 登録

### 優先度 C: 条件付き対応

- MCP 2026-07-28 / TypeScript SDK v2 への移行
- 評価データで必要性が証明された場合だけ、セマンティック検索またはハイブリッド検索
- 実利用の要望が確認された場合だけ、他言語版 SCP Wiki への拡張

## 非対象

- MCP Apps による GUI
- サーバー内 LLM、sampling、AI 要約、回答生成
- Tasks など長時間非同期処理
- ベクトル DB、GraphRAG、知識グラフの先行導入
- SCP 画像の収集、再配布、画像認識、個別メディアの権利判定
- OAuth、ユーザーアカウント、課金
- 書き込み系 Tool
- 一度に多数の新 Tool を追加すること
- 利用実績のない段階での多言語データ全量対応

## 実装項目

### 1. SCP-173 固有警告の削除

目的: 個別メディアの権利判定に当たる SCP-173 固有処理を削除する。

- ドキュメント先行変更:
  - `docs/要件定義.md` から旧画像固有警告の必須要件を削除する。
  - `仕様書.md` から `media_warnings` と SCP-173 特例を削除する。
  - `README.md` から SCP-173 固有警告を削除する。
- TDD:
  1. `media_warnings` が公開レスポンスに存在しないことを示す失敗テストを追加する。
  2. ハードコード処理と型定義を削除して Green にする。
  3. 不要になった fixture・説明を整理し、全テストを再実行する。
- 完了条件:
  - Tool、Resource、Prompt のいずれからも SCP-173 固有警告が返らない。
  - 全ページ共通の出典・作者・CC BY-SA 情報は維持される。
  - 別形式の包括的な警告を追加していない。
- 互換性:
  - 公開レスポンスからフィールドを削除するため、README と仕様書に変更内容を記載する。

### 2. 現行 SCP Data API 契約への適合

目的: ライブデータに対して検索・取得を正常に動かす。

- ドキュメント先行変更:
  - コレクションごとの index / content 配置を `仕様書.md` に定義する。
  - 一意識別子を `collection + page_id` とする。
- TDD:
  1. 同一 `page_id` の別ページ、Tales の絶対パス、GOI の単一 content ファイルを fixture 化して Red にする。
  2. パスの basename 検証、コレクション別解決、一意キー生成を最小実装する。
  3. SSRF 許可境界と既存 API を保ったまま整理する。
- 完了条件:
  - `scp_search` が重複 ID で例外終了しない。
  - Items、Tales、GOI の代表ページを検索・取得できる。
  - 外部 index 内の絶対パスをそのままローカルパスや任意 URL として使用しない。
  - fixture テストに加え、失敗時に通常 CI を不安定化させないライブ canary の実行方法を文書化する。

### 3. 作者・帰属情報の正確化

目的: ページ作成者と履歴編集者を混同せず、AI が正しい帰属情報を引用できるようにする。

- ドキュメント先行変更:
  - `authors` の意味を「取得できたページ作者」に限定する。
- 実装方針:
  - 公式 Licensing Guide が案内するSCPPERのページAPIから作品作者を取得する。
  - SCP Data API の `creator` / `created_by` と `history` は作者一覧に含めない。
  - SCPPERを利用できない場合は作者不明として返し、本文取得は継続する。
- TDD:
  - SCP-173 の作成者と編集者が分離される fixture テストを先に追加する。
- 完了条件:
  - 履歴編集者の全員を `authors` として返さない。
  - 作者を取得できない場合も、本文・一次出典・ライセンスを返す。
  - SCPPER以外の外部 API 依存を追加しない。

### 4a. 検索方式の計測と選定

目的: 計測結果に基づいて CLI に適した検索方式を決める。

- 比較対象:
  - 現行の全件インメモリ MiniSearch
  - ビルド時に生成する読み取り専用・分割済み字句索引
  - 読み取り専用 SQLite FTS スナップショット
- 計測項目:
  - cold start、warm search、最大 RSS、成果物サイズ、更新手順、出典追跡、オフライン再現性
- 暫定目標:
  - cold search 5 秒以内
  - 最大 RSS 512 MB 以下
  - 目標値は代表環境での計測結果を添えて確定し、達成のために品質や出典を落とさない。
- 選定結果:
  - 各コレクションのメタデータを使うMiniSearchを採用する。
  - 本文は検索後にオンデマンド取得し、検索索引には保持しない。
  - 静的索引の同梱は日次更新との不整合、SQLite FTSは配布依存の増加を招くため採用しない。
- 完了条件:
  - 比較結果と採否理由を `仕様書.md` または ADR に記録する。
  - 採用方式の実装を混在させない。

### 4b. 選定した字句検索方式の実装

目的: 4a で選定したメタデータ字句検索を実装し、検索の初回体験を改善する。

- TDD:
  - 順位、フィルター、ページ種別、重複 ID、索引不在・破損時の期待挙動を先に固定する。
  - 同じ入力から同じ索引を再生成できることを検証する。
- 完了条件:
  - 4a で確定した性能目標を代表環境で満たす。
  - 検索結果から一次データのページ URL と本文取得へ追跡できる。
  - 常駐 DB、外部検索 SaaS、ベクトル DB を追加しない。

### 5. 範囲指定取得と引用位置情報

目的: 長文ページを必要な範囲だけ取得し、AI が引用箇所を再確認できるようにする。

- API 方針:
  - `scp_get_content` に `start_line` と `max_lines` を追加する。
  - 新しいToolや見出し解析は追加しない。
- 出力:
  - `content_hash`
  - `range`: `start_line`、`end_line`、`total_lines`、`has_more`
- TDD:
  - 長文分割、範囲上限、本文外の開始位置を先にテストする。
- 完了条件:
  - ページ全体を毎回返さずに目的の範囲へ到達できる。
  - 返却テキストと位置情報・ハッシュの対応を検証できる。
  - 出典・作者・ライセンスが部分取得でも欠落しない。

### 6. MCP クライアント向け構造化契約

目的: クライアントと AI が Tool の安全性と出力形式を事前に理解できるようにする。

- 対象:
  - `outputSchema`
  - `readOnlyHint: true`、`destructiveHint: false`、外部データ取得を示す annotation
  - MCP Resource Link または同等の標準的な出典リンク表現
  - Tool / Resource / Prompt 間での安全・レート制限・監査経路の一貫性
- 完了条件:
  - 全 Tool の構造化出力が schema と一致する。
  - 読み取り専用性を対応クライアントが機械的に認識できる。
  - 独自メタデータを増やさず、MCP 標準で表現できるものを優先する。

### 7. npm CLI 配布と MCP Registry 登録

目的: インストール方法を短くし、MCP 利用者が発見できるようにする。

- 前提: 2〜4b の検索・帰属情報に関する修正が完了していること。
- 対象:
  - `bin` と実行エントリーポイント
  - `repository`、`homepage`、`keywords`、MCP 用 package metadata
  - `server.json`
  - npm 公開用 dry run と、公式 MCP Registry の検証・公開手順
  - README の `npx`、stdio、HTTP 設定例
- 完了条件:
  - clean 環境で package を導入し、stdio の initialize と代表 Tool を実行できる。
  - `npm pack --dry-run` に不要ファイルや秘密情報が含まれない。
  - Registry metadata が公式 validator を通る。

### 8. MCP 2026-07-28 / SDK v2 追従（条件付き）

目的: SDK v2 の安定性と利用クライアントの対応を確認した後、保守性と相互運用性を改善する。

- 着手条件:
  - SDK v2 の移行ガイドと互換性が確認できる。
  - 対応対象クライアントで接続試験ができる。
  - 必須修正と配布対応を遅らせない。
- 対象:
  - 可能な範囲で stateless HTTP 化し、プロセスメモリ内の session Map を減らす。
  - stdio 互換性を維持する。
- 完了条件:
  - 対象クライアントで stdio / HTTP の契約テストが通る。
  - 旧 SDK からの挙動差とロールバック方法が文書化される。

## 関連プロジェクトとの比較

| 比較対象             | 参考にする強み                                 | SCP-MCP での判断                                                     |
| -------------------- | ---------------------------------------------- | -------------------------------------------------------------------- |
| Wikipedia 系 MCP     | 節指定、長文ガード、多様な導入方法             | 節単位取得と導入性は採用する。百科事典一般への拡張はしない。         |
| MediaWiki 系 MCP     | 標準 API を利用した検索・取得                  | SCP Wiki は Wikidot のため、そのまま移植せず出力契約だけ参考にする。 |
| Context7 系          | パッケージ発見性、短い導入経路、引用可能な文脈 | 配布 UX は参考にする。中央集約サービスやLLM処理は持ち込まない。      |
| SCPPER               | SCP ページの作者・別名などの補完情報           | 帰属精度の補助候補。本文の一次データ源にはしない。                   |
| 汎用ベクトル検索 MCP | 意味検索、曖昧な質問への想起率                 | 評価データで字句検索の不足が示されるまで見送る。                     |

SCP-MCP では、SCP 固有のページ種別を横断し、本文・作者・ライセンス・引用位置を一貫した形式で返すことを重視する。

## 全体の受入指標

### 正確性

- Items、Tales、GOI の固定評価セットで検索から本文取得まで成功する。
- ページ作成者と編集者を混同しない。
- 部分取得でも URL、作者、ライセンス、位置情報が欠落しない。

### 性能

- 検索方式は 4a で確定した cold start、RSS、成果物サイズの基準を満たす。
- 代表的な本文取得で全コーパス索引を再構築しない。

### 安全性

- 全 Tool が読み取り専用である。
- 許可ホスト、リダイレクト、サイズ上限、timeout、レート制限を維持する。
- SCP コンテンツを命令として実行せず、検知情報を構造化して返す。

### 配布性

- clean 環境から documented command で起動できる。
- stdio と HTTP の initialize、代表検索、代表取得を自動検証できる。
- npm と MCP Registry の metadata が公式検証を通る。

## リスクと抑制策

- 外部データ形式の再変更:
  - コレクション別 fixture と任意実行の live canary を分け、CI を外部障害に直結させない。
- 補助 API 依存の増加:
  - 作者補完は失敗可能な補助経路とし、本文取得と一次出典を阻害しない。
- 索引成果物の肥大化:
  - 4a でサイズを比較し、生成物の同梱前に更新頻度と配布コストを確認する。
- Tool 増加による選択精度の低下:
  - 既存 Tool の引数で表現できる場合は追加しない。
- SDK 移行による互換性低下:
  - 中核改善から分離し、対象クライアントの契約テスト後に着手する。
- 仕様変更の同時混入:
  - 各実装項目で変更目的、参照セクション、互換性への影響、ロールバック方法を明示する。
